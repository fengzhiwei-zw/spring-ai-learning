# 现有功能检查与修复说明

本次范围是仓库中已经存在的对话、结构化输出、多模态、会话记忆、RAG、工具调用、日志、文档入库及长期记忆辅助类。没有新增 Agent 接口、MCP、登录系统或文档上传接口。

修复依据是项目实际使用的 Spring AI 2.0.0 源码和可重复回归测试。在线参考文档可能已经更新到其他补丁版本，不能直接用文档中的新 API 替代本地依赖中的 API。

## 1. RAG 误伤普通对话和结构化提取

原实现把同一个带 RAG 的 `ChatClient` 注入所有示例。知识库为空时，默认 `ContextualQueryAugmenter` 会把问题替换为要求模型说明无法回答的提示词。即使问候或天气查询本身不依赖文档，也可能变成拒答。

另一个问题是查询改写会改变输入文本。代码审查和信息提取需要精确保留用户输入，不能先把代码或待提取文本改写成检索问题。

修复后有两个客户端：

- `chatClient`：保留原有 RAG、会话记忆和天气 / 时间工具。通过 `allowEmptyContext(true)`，空召回时继续普通回答。
- `structuredChatClient`：用于代码审查、书籍推荐、股票信息提取和图片理解，保留记忆与日志，不装配 RAG 和天气工具。

`Stage3Controller` 中的普通 `/api/v3/chat` 继续使用对话客户端。空检索回退只处理“查询成功但没有内容”的情况，不会吞掉 Chroma 连接失败等基础设施故障。

对应代码：`ChatClientConfig`、`Stage3Controller`。

## 2. 结构化输出只有反序列化，没有完整校验

原来的 `.entity(StockInfo.class)` 负责解析对象。仅添加 `@NotBlank`、`@Min` 和 Validation 依赖，并不会自动启用 Schema 纠错和所有业务校验。

尤其是 `double price`：模型漏掉价格字段时，反序列化可能得到默认值 `0`，而 `@Min(0)` 又会接受这个值，造成“没有提取到价格，却看起来成功了”。

修复分两步：

1. ChatClient 结构化接口显式调用 `.entity(..., spec -> spec.validateSchema())`，让不符合 Schema 的 JSON 得到有限次数的反馈重试。
2. 解析完成后执行 Jakarta `Validator.validate()`。`StockInfo.price` 改为带 `@NotNull` 的 `Double`；书籍必填字段、出版年份和用户年龄等也做业务校验。

书籍列表除了检查每一个元素，还检查返回数量是否等于请求数量。请求 `count` 限制在 1～10，避免无效输入和无限制生成。

重试有上限，不能保证模型最终一定合规。最终仍无效、无法解析或返回空对象时，接口返回 502，不把错误对象当成成功结果。Jackson 3 的解析异常也被转换为明确的错误，不把原始模型内容直接暴露给客户端。

对应代码：`Stage3Controller`、`Stage4Controller`、`AiResponses`。参考：[结构化输出与显式 Schema 校验](https://docs.spring.io/spring-ai/reference/api/structured-output.html)。

## 3. 手动调用 ChatModel 的消息顺序和记忆写入时机

`Stage4Controller` 原来先把用户消息写进记忆，再调用模型，而且把 SystemMessage 放在消息列表末尾。这有两个结果：模型调用失败时留下半轮记忆；当前系统指令也没有放在最前面。

现在先构造本次 Prompt：当前系统指令 → 历史非系统消息 → 本次用户输入。历史系统消息不会覆盖当前角色设定，也不会修改仓库返回的历史列表。

`/api/v4/model` 在取得有效文本后，一次性添加本轮用户与助手消息；返回值由 `ChatResponse.toString()` 改为真正的回答文本。

`/api/v4/format` 还会等待 JSON 转换及业务校验成功后才保存整轮。Schema 提示放进当前系统消息，不作为用户原话写回历史。调用失败、解析失败和负数年龄都不会改动原有记忆。

这里的成功后保存针对 `/api/v4/*` 的手动记忆实现；ChatClient 示例仍使用框架的 `MessageChatMemoryAdvisor`，其用户消息写入时机遵循框架实现。

## 4. 不同访问者共用默认会话

原来的 `default-session` 是一个全局固定字符串。所有不传 `sessionId` 的请求都落到同一份 Redis 历史，会发生上下文串线。

现在不传 ID 时，使用当前 HTTP Session 的独立 ID。浏览器会自动携带会话 Cookie；curl 如果不显式传 ID，需要用 Cookie 文件维持会话。

显式传入的 `sessionId` 保留原有使用方式，并拒绝空白、控制字符和超过 128 字符的值。它仍然只是客户端持有的会话键，本次没有新增身份认证，不能把“知道一个会话 ID”当成已经完成会话归属授权。

对应代码：三个 Controller 和 `ConversationIds`。跨会话隔离、同一会话连续访问和旧客户端显式 ID 均有回归测试。

## 5. 空响应和可缺省元数据导致异常

`/chat/detail` 原来依赖 `assert` 判断响应存在。Java 运行时通常不启用断言，这些检查不足以保证后续解引用安全。`Map.of()` 也不能保存 null，模型或用量字段缺失时可能直接抛异常。

修复后先显式检查响应、Generation 和有效文本。缺失有效回答返回 502；可缺省的模型和 Token 字段通过 `LinkedHashMap` 保留 null，不因元信息缺失丢掉有效回答。框架提供的 `EmptyUsage` 仍遵循其默认零值语义，不在应用中把缺失值强制改成零。

其他同步文本接口也增加了空回答检查。客户端参数增加非空白及长度限制，错误参数在调用模型之前返回 400。

## 6. 图片接口引用不存在的资源

原来的 `static/demo.png` 没有提交到仓库，接口在读取图片时就会失败。

现在补充了一张红、绿、蓝三色 PNG 测试图片，并提供 `AI_IMAGE_MODEL` 配置，允许图片接口选用具备视觉能力的模型。测试验证图片实际被读取并附加到 UserMessage，同时验证请求使用配置的视觉模型。

图片资源存在不代表任意模型都具备视觉能力。真实环境仍需选择账号有权限使用的视觉模型。

## 7. 工具循环没有执行上限，模拟天气标识不完整

框架提供工具执行循环，但项目没有设置业务侧上限。模型若持续请求工具，会不断调用下去。

`LimitedToolCallingAdvisor` 继承已有 `ToolCallingAdvisor`，沿用框架执行逻辑，在每一批工具执行之前检查：

- 默认最多执行 5 轮工具。
- 默认累计最多执行 10 个工具调用，同一轮多个调用也计数。
- 超限批次不会执行，返回明确错误；同步和流式路径都使用相同规则。
- 计数状态属于单次请求，不在多个请求之间共享。

这不是完整 Agent 的总预算。单次对话 / Embedding 请求配置了 60 秒超时，但任务总时限、所有轮次总 Token 等尚未实现。

天气工具原来只有默认城市分支标记模拟数据，北京、上海、广州的固定结果却看起来像实时数据。现在工具描述和所有分支都明确标记模拟数据，并校验城市参数。工具日志改为标准日志事件 `weather.tool.called`。

## 8. 流式调用缺少日志，正文脱敏存在遗漏

原来的日志类仅实现 `CallAdvisor`，SSE 不经过这条日志路径。它的位置还在工具循环内部，一条日志表示单次下游模型调用，无法代表完整的客户端请求耗时。

现在同时实现 `StreamAdvisor`，在外层记录订阅开始、正常完成、失败和取消。使用 `Flux.defer()`，订阅时才开始执行；不会自行订阅、吞掉异常或阻断取消。测试验证原始文本片段保持原顺序，错误对象继续向下传播，取消能够到达上游 Publisher。

默认仍不记录 Prompt 和回答正文。开启正文 DEBUG 日志时，脱敏规则补充了 JSON 引号、带空格的密码及 Bearer Token，避免只处理 `key=value` 而遗漏 `"api_key":"..."`。

日志耗时覆盖当前 ChatClient 请求链；Token 字段仍来自最终响应元数据，不能当成查询改写和全部工具轮次的累计费用。SSE 若已发送响应头，后续错误也不能再把 HTTP 状态改为 502；本次保留原有文本 SSE 协议，让异常继续传播并记录日志，没有新增事件协议。取消到达上游 Publisher 也不等于已经验证远端模型服务取消了生成。

## 9. 配置来源分裂，手工 Redis 仓库忽略部分配置

原来对话模型读取 YAML，而 Embedding 的 API Key 直接读取系统环境变量，Embedding 模型、维度和 Chroma 地址写死在 Java 中。通过 IDE 参数或其他 Spring 配置源覆盖配置时，可能只有对话部分生效。

现在 Embedding 与对话复用 Spring 配置中的服务地址和 API Key，Embedding 模型、维度、超时，Chroma 地址及 collection 均由 YAML 注入。

手动声明 `RedisChatMemoryRepository` 会让仓库自动配置退让，因此 TTL、索引名等不会自动应用。现在显式从本地 2.0.0 的 `RedisChatMemoryProperties` 应用初始化开关、索引名、前缀、TTL、查询上限和元数据字段。回归测试验证自定义索引、前缀、TTL 和消息上限确实进入仓库配置。

原有 collection 默认名称保留，避免修配置时突然找不到已有数据。切换 Embedding 模型或维度仍应使用新 collection 并重新导入。

## 10. 文档入库的重复、更新和空内容处理

原来的分块每次生成新的文档 ID，重复导入相同文件会留下重复片段，文档更新后也没有清理旧内容。

现在对可读资源执行以下流程：

1. 拒绝不存在的资源，过滤空白片段；没有有效文本时不调用向量库。
2. 对稳定来源地址计算 `source_id`，根据分块文本计算内容版本。
3. 使用来源、版本、片段序号生成稳定 ID。当前 Chroma 存储按 ID upsert，重复导入相同内容不会再增加片段副本。
4. 新版本写入成功后，再删除同一 `source_id` 的其他版本。写入失败时不会先清空旧知识。

Service 内串行处理导入，避免同一进程并发更新互相清理。无稳定地址的内存资源按内容识别；不同内容无法自动认定为同一文档的新版本。旧代码产生的数据没有 `source_id`，不会被自动删除。

写入和清理是两步操作，不具备跨服务事务；清理失败时可能暂时保留新旧版本，需重试导入。没有引入分布式导入锁或历史数据迁移。

构造器也补上 `@Qualifier("knowledgeVectorStore")`，明确指定知识库，避免依赖参数名推断来区分两个 VectorStore。

## 11. 长期记忆辅助代码的结构和 ID 边界

原来用 `substring()` 截断拼接后的记忆文本，可能截断标签、转义实体或 Unicode 代理对。现在按更新时间优先选择能放入预算的完整条目，超大条目跳过，不生成破损结构。

记忆写入 ID 原来用分隔符连接租户、用户和逻辑键。若这些值本身含有同样的分隔符，不同组合可能形成同一个输入字符串，覆盖彼此的数据。现在拒绝保留分隔符，同时统一拒绝租户 / 用户 ID 两侧的空白，避免写入保留空格、检索却裁掉空格造成无法命中。

这些修复只维护已有辅助类。长期记忆仍未加入默认 Advisor 链，也没有新增事实提取或写入入口。
